# 第九章 技术写作样例：好的中文技术文章长什么样

> 样例：阮一峰 60 篇、陈皓（酷壳）60 篇、美团技术团队 60 篇，另有 1 篇 InfoQ 文章作为案例，2026-10-18 收集。目录和逐篇统计见 [`corpus/`](../corpus/)。阮一峰的文章按其许可收录全文，其他只有链接和统计。

前几章讲 AI 味是什么。这一章换一个方向：**人写的好技术文章，到底有什么特征？**三个来源分别代表三种常见的技术写作：讲解教程、观点评论、工程实践报告。

## 一、三种写法的数字

所有数字都是每篇文章的**中位数**（"每千字"按正文的中文字数算，不含代码块和链接）。

| 特征 | 阮一峰（讲解） | 陈皓（观点） | 美团（工程报告） |
|---|---|---|---|
| 篇幅（中文字数） | **1,211** | 2,531 | **4,483** |
| 含代码的文章 | 27 / 60 | 22 / 60 | 31 / 60 |
| 段落长度（字） | **17** | 55 | 64 |
| 句子长度（字） | **21.5** | 34.0 | 38.0 |
| 句长变异系数 | 0.51 | 0.75 | 0.65 |
| 每千字小标题 | 1.7 | 1.2 | **4.2** |
| 列表行占比 | 0%* | 27% | **55%** |
| 每千字"我" | 1.7 | **4.7** | 0.0 |
| 每千字"我们" | 0.6 | 3.3 | 3.9 |
| 每千字判断词（我认为、建议、不要、其实……） | 0.5 | **1.8** | 0.3 |
| 每千字软化词（可能、也许、未必……） | 0.8 | 1.2 | 0.7 |
| 每千字数字 | 13.8 | 7.1 | 12.6 |
| 有"总结 / 小结"一节的文章 | 0% | 8% | **42%** |
| `aiflavor` 指数 | 19.2 | 24.0 | **29.6** |

\* 阮一峰常把列表写在段落里（"（1）……"），统计规则只认 `- ` 和 `1. ` 开头的行，所以这一项偏低。

## 二、三种写法的特点

### 阮一峰：一段一个意思

- **很短**：一篇约 1,200 字。段落中位数只有 17 字，很多段落只有一句话。
- **开头有固定的三步**：先给一个具体事实，再提出问题，最后才说这篇文章要做什么。

  > 2013年发布至今，Docker 一直广受瞩目，被认为可能会改变软件行业。
  >
  > 但是，许多人并不清楚 Docker 到底是什么，要解决什么问题，好处又在哪里？本文就来详细解释……
  >
  > —— 阮一峰，《Docker 入门教程》（2018）

- **几乎不用"我"**，也很少下判断，口吻是平静的讲解。
- **从不写"总结"一节**，常以"（完）"结束。
- **句子长短很均匀**（变异系数 0.51，三人里最低）。这说明"句子长短太均匀"在技术讲解里**不一定是 AI 味**，短句、短段落本身就是清楚的写法。

### 陈皓：用"我"下判断

- **"我"用得最多**（每千字 4.7 次），**判断词也最多**（是阮一峰的 3.7 倍、美团的 6.1 倍），软化词也最多：判断很多，但会留余地。
- 句子长、长短变化大（变异系数 0.75），读起来像在说话。
- 12% 的文章开头就是"这篇文章……""本文……"，开头直接说要写什么，在他这里是一种直率，不是套话。
- 他也会用今天被当成"AI 味"的说法。2007 年的《C++ 虚函数表解析》里有一句"言归正传，让我们一起进入虚函数的世界"，这正是英文 AI 腔 "let's dive in" 的中文版。**这些说法是 AI 从人那里学来的，不是 AI 发明的。**

### 美团技术团队：结构化的工程报告

- **最长**（中位数约 4,500 字），**结构最重**：每千字 4.2 个小标题，55% 的行是列表，42% 的文章有"总结"一节。
- 用"我们"，几乎不用"我"，也几乎不下个人判断，是团队的口吻。
- **`aiflavor` 分数最高**（29.6）。命中最多的是"加粗小标题 + 冒号""当……时""有以下几种情况""一方面……另一方面""全方位 / 多维度"。

## 三、这对"AI 味"研究意味着什么

**1. 人写的技术文章也会触发很多"AI 味标记"。**三个来源都有命中，团队技术报告最多。这印证了第五章说的局限，也说明第三章的标记清单是在描述一种**文体**，不只是 AI：模型学的正是这类结构化、模板化的报告。

**2. 同一个标记，在不同文体里意思不同。**第六章的散文实验里，"不是……而是……"是最明显的 AI 标记（模型 14 次，鲁迅和朱自清 0 次）。但在技术文章里，阮一峰用了 15 次，陈皓用了 30 次。在技术讨论里，用它来纠正一个常见误解很自然。**所以不能把一份标记清单用在所有文体上。**

**3. "本文将介绍"不一定是 AI 味。**阮一峰几乎每篇都有"本文……"，但它放在一个具体事实和一个问题之后。AI 的写法往往是**第一句话就是**"本文将介绍……"，前面什么具体的东西都没有。区别不在这几个字，而在它前面有没有内容。

**4. 句长均匀也一样。**阮一峰的句子最均匀，但他的文章显然不是 AI 写的。技术讲解里的短句短段落是一种清楚的选择。

## 四、案例：AI 味分数最高，但内容很扎实

用户指定加入的一篇 InfoQ 文章：《3 年、1 万人，快手技术团队首次系统披露 AI 研发范式升级历程》（快手技术团队，审校陈姚戈，2026-02-09）。

| | 这篇文章 | 美团（中位数） |
|---|---|---|
| 篇幅 | 11,967 字 | 4,483 字 |
| 每千字数字 | **19.0** | 12.6 |
| 每千字"我们" | 6.4 | 3.9 |
| 每千字"我" / 判断词 | 0 / 0.25 | 0 / 0.3 |
| `aiflavor` 指数 | **42.5** | 29.6 |

它是这批样例里 `aiflavor` 分数最高的：命中"全流程"8 次、"重塑"4 次、"在 AI 时代"3 次，还有"赋能""众所周知""深度融合"；编者按是典型的宣传口吻，结尾是招聘广告。（"全流程"在研发流程里是一个真实的概念，这几次命中有一部分是误判。）

但它的内容很扎实：
- 有一个清楚、反直觉的主张：**用 AI 开发工具 ≠ 个人提效 ≠ 组织提效。**
- **承认自己结果里的矛盾**：AI 代码生成率超过 30%，个人主观效率提升明显，但组织的需求交付效率基本没变。
- 数据很多：工具渗透率 >95%，人均需求吞吐量提升 41.57%。

**这正好说明：形式上的"AI 味"和"没有信息"是两回事。**这篇文章是企业公文腔，但信息量大、有真实的发现；`aiflavor` 只看形式，在这里的分数会误导人。第二章引用的研究发现，最能预测"AI 垃圾文"的是信息密度低和跑题，这才是判断技术文章好坏的关键。

## 五、对三位作者的评价

> 这是维护者和 AI 助手的判断，基于抽样阅读和上面的统计，不是实验结论。快手只评价这一篇文章，不代表快手技术团队的整体水平。陈皓先生已于 2023 年去世，GitHub 上的几个存档都是网友为纪念他保存的。

| | 一句话 | 最强 | 最弱 |
|---|---|---|---|
| 阮一峰 | 把东西讲清楚的大师 | 清晰、耐心、门槛低 | 个人判断少，深度有限 |
| 陈皓 | 有立场的老工程师在说话 | 判断、经验、独立思考 | 有时偏激、粗糙，后期夹带推广 |
| 快手（InfoQ） | 有料的企业报告，穿着公文腔的外衣 | 数据、方法、敢承认矛盾 | 宣传腔重，数据口径不清 |

**阮一峰。**讲解的节奏极好：讲闭包时，先说"正常情况下办不到"，再给"变通方法"，接着马上上代码，读者每一步都知道为什么要往下看。克制，不渲染，不升华。局限是几乎没有个人判断（每千字判断词 0.5 次），讲解型写法天然会省略边界情况，适合入门，不适合当权威参考。今天 AI 写教程的结构和他很像，但学不来他的例子选择和克制。

**陈皓。**敢下判断，而且给理由：《是微服务架构不香还是云不香？》先指出"这些文章要的是流量……我觉得有 80% 的人只看标题"，再逐条拆原文，最后写"下面是我的独立思考，供你参考"。判断背后是真实的工程经验（能指出问题在 Step Function 的伸缩和按状态转换收费）。会用反讽（《如何超过大多数人》）。三位里最不像 AI。局限是有错别字和口误，有时情绪先于论证；后期文章会推荐自己公司的产品；2009–2011 年的 539 篇大多是转载和短评（中位数 411 字），真正的陈皓是 257 篇长文。

**快手（InfoQ）。**核心发现很有价值，也很诚实：工程师主观感觉编码效率提升 20–40%，AI 代码生成率超过 30%，但组织的需求交付效率基本不变。有具体的诊断过程（数据 → 访谈 → 根因是客户端架构劣化），有好比喻（让 AI 编程工具从"临时工"变成"熟悉业务的开发工程师"）。局限是宣传腔重、结尾是招聘和产品推广；"20–40%"是主观体感，"人均需求吞吐量提升 41.57%"没有说明定义和对照；经过研发效能委员会审稿，是精心整理的官方叙事；1.2 万字太长。

**放在一起看：阮一峰讲清楚，陈皓讲观点，快手讲事实。**最好的技术文章是三者合一：讲得清楚，有自己的判断，每个判断后面都有事实。

## 六、写技术文章可以学什么

| 想写成哪一种 | 学谁 | 关键做法 |
|---|---|---|
| 教程、入门、概念解释 | 阮一峰 | 一段一个意思；先事实、再问题、后承诺；例子和代码紧跟在概念后面；写完就停，不写"总结" |
| 技术评论、经验、选型 | 陈皓 | 用"我"写出判断和理由；该留余地的地方明说"可能""未必"；讲自己踩过的坑 |
| 项目复盘、方案设计 | 美团 | 问题 → 方案 → 数据 → 效果；用小标题和列表帮读者扫读。**但要小心**：结构一重就容易变成模板，每一节都要有具体数字和取舍，不要只有"全方位提升" |

结合第四章的方法，写技术文章时最有效的仍然是：**你提供真实的素材**（命令、日志、报错、测试数字、没成功的尝试）和**你的判断**，AI 只负责组织和查漏。第三列的风险，正好是 AI 起稿时最容易出现的问题。

## 七、局限

- **统计依赖网页提取。**比如阮一峰的代码块在原网页里放在引用块中，很早期的文章把代码写在普通段落里；列表的写法也各不相同。数字只能看方向和量级。
- **时间不一样。**阮一峰的技术分类页只列到 2019 年；酷壳原站文章页现在报"数据库错误"，取自 GitHub 上的 Markdown 存档 [slan-ning/coolshell-markdown](https://github.com/slan-ning/coolshell-markdown)，2004–2023 年每年轮流抽样，只取 1,500 字以上的文章；美团是 2013–2022。
- **美团是多人写的**，统计反映的是团队的平均风格，不是某一个人。
- **只有三个来源**，知乎的两位作者因为没法在不批量抓取的情况下确认作者，暂时没有收录。
